# GinyScreen 技术路线与选型（v2.0 决策记录）

> 本文记录 v2.0 重建时的关键选型与替代方案对比，供后续演进参考。
> GinyVoC 时代（v0.6 及以前）的旧版对比分析已并入本文末尾「历史存档」。

---

## 一、v2.0 选定的路线

```
客户端（浏览器/Electron）
 ├── 标准链路：WebRTC（P2P mesh + 内置 TURN 兜底）
 ├── 影院链路：WebCodecs 编码 + Socket.IO 二进制中继
 └── 信令/房间：Socket.IO（单服务器单房间）

服务器（Node.js，可嵌入 Electron）
 ├── 信令 + 房间状态 + 影院码流转发 + HTTP API
 └── 网络能力层
      ├── 内置 STUN/TURN（turn-server，纯 JS）
      ├── UPnP-IGD / NAT-PMP 端口映射（@achingbrain/nat-port-mapper）
      ├── STUN 公网探测 + NAT 类型（RFC 5780）
      ├── 自签名证书自动生成（selfsigned）
      └── 网络诊断报告（doctor）
```

### 为什么是这套

| 需求 | 选型原因 |
|------|----------|
| 用户痛点①「画质不稳定」 | 双链路：WebRTC 做低延迟 + WebCodecs 自控编码做稳定画质；并把「直连/中继、码率、丢包、拥塞原因」暴露到质量面板 |
| 用户痛点②「需要外置联机软件」 | 内置 TURN + UPnP + IPv6 + 局域网：把「装 VPN」变成「发个地址」，且全部能力内嵌、无第三方依赖 |
| 自托管极简 | 单 Node 进程；客户端无构建步骤；桌面版一个 exe |
| 小圈子（2~4 人） | mesh 延迟最低、服务器零媒体成本；中继兜底连通性；>8 人再上 SFU |
| 跨设备 | 浏览器即客户端（含 Safari/iOS 观看）；PWA 可安装；桌面版 Windows exe |

## 二、替代方案对比（联机部分）

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **内置 TURN + UPnP + IPv6**（选定） | 零外置软件、无第三方依赖、可诊断 | 依赖路由器 UPnP 或 IPv6；对称 NAT 需中继 | ✅ 默认路径 |
| 组网工具（Radmin/蒲公英/ZeroTier） | 连不通时最稳 | 要所有人安装；免费额度/注册；VPN 中继带宽小（画质杀手） | 降级为高级备选 |
| 内网穿透（SakuraFrp 等） | 只有开服者要装 | 需实名；隧道带宽与稳定性受服务商限制 | 高级备选 |
| 公共 STUN/TURN 服务 | 免部署 | 第三方可用性/隐私风险；国内可达性差 | 仅作 STUN 兜底（公共 STUN 列表） |
| 自建云中继（VPS 跑 TURN/SFU） | 连通性最好、可扩容 | 需要买服务器与带宽；国内带宽贵 | 路线图（可选模式） |

## 三、替代方案对比（媒体部分）

| 方案 | 优点 | 缺点 | 结论 |
|------|------|------|------|
| **WebRTC mesh + WebCodecs 中继**（选定） | 低延迟 + 稳定画质两条路；零媒体服务器成本 | 上行随人数增长；两条链路的维护成本 | ✅ |
| 纯 mesh（v1.x 现状） | 最简单 | 弱网画质抖动（用户痛点）；无观测手段 | 已被 v2 取代 |
| mediasoup SFU（自建） | 几十人；选择性转发/层选择 | 需公网服务器 + 端口规划；桌面版分发复杂 | 频道 >8 人时升级（信令协议可复用） |
| LiveKit（整体迁移） | 功能完整、生态好 | 重写房间模型；自托管免费版并发限制 | 若转向完整会议产品再评估 |
| Go + Pion（单二进制） | 部署最简；性能好 | 全部重写；前端仍需 WebRTC | 远期 |
| 原生客户端（C++/Rust/Qt） | 延迟天花板最高 | 开发/维护成本最高 | 不做 |
| Fork 开源（Galène/Mumble） | 起步快 | 定制受限、依赖上游 | 备选 |

## 四、关键技术取舍记录

| 决策点 | 选择 | 理由 |
|--------|------|------|
| TURN 实现 | `turn-server`（纯 JS，可嵌入） | 零外置依赖、跨平台、可随桌面版分发；对小规模场景足够（协议覆盖完整：UDP/TCP/TLS/WS、REST 凭据、配额、hooks） |
| 是否上 SFU | 暂不上 | 目标场景 2~4 人；mesh 延迟最低、零成本；信令与媒体层已隔离，后续可替换 |
| 影院模式编码器 | 默认 H.264（硬件优先），可回退 VP9/AV1/VP8 | 硬件编码普及、兼容性最好（Safari/移动端解码也稳）；VP9/AV1 压缩率更高但软编吃 CPU |
| 影院模式传输 | Socket.IO 二进制 + `volatile` | 复用现有信令连接；`volatile` 天然「丢旧不积压」，延迟有上界；无需引入 WebTransport/QUIC 复杂度 |
| 前端工程 | 保持零构建（原生 ES Modules） | 自托管友好、Debug 方便、Electron 打包简单；代价是没有类型检查（用测试与代码评审补） |
| 语音功能 | 移除 | v1.4.0 实测无法正常使用；产品定位「专注屏幕共享」（用户明确要求） |
| 自动更新 | 自研多源清单 + NSIS 静默升级 | 国内网络友好（代理/镜像竞速）；electron-updater 依赖单一发布源 |

## 五、历史存档（GinyVoC 时代对比，v0.6 及以前）

> 以下为旧版（语音频道时代）的路线对比，结论已被 v2 决策取代，仅作背景资料。

- 路线 A：保留 Web 客户端 + mediasoup SFU（改动小、可扩容）
- 路线 B：整体迁移 LiveKit（功能完整、重写房间模型）
- 路线 C：Go + Pion 全自研（单二进制、成本高）
- 路线 D：原生桌面客户端（Mumble 式，成本最高）
- 路线 E：Fork 开源项目（Galène / harmony-server）

当时的建议：继续打磨 mesh + Electron 路线，>8 人时优先 mediasoup。
v2 的判断：**在该建议之前，先用「内置中继 + UPnP/IPv6 + 双链路画质」解决真实用户的首次使用与画质痛点**；
SFU 仍是人数增长后的下一步。
